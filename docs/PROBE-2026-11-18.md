# RemoteFM14Move phase 0 probe: results (2026-11-18, on the owner's Move, with their OK)

Read-only ssh, plus two benchmark binaries in /data/UserData/rfm14move-probe/ (still there, ~8 MB; delete when done).
Move Remote (moveremote-host) was running during the probe, so Move's own software was stopped. Nothing was stopped,
started or installed into Schwung.

## The system
- **Hardware:** 4x Cortex-A72 (part 0xd08) at 1.5 GHz, governor `performance`.
- **OS:** kernel 5.15.92-rt57 PREEMPT_RT, glibc 2.35, BusyBox. The bookworm cross build must not need symbols newer
  than glibc 2.35; ours needed only 2.34.
- **RAM:** 1849 MB in all, 1715 MB available with Move stopped.
- **Disk:** /data has 52.8 GB, 49.6 GB free (the same partition as Schwung). The root fs is full (10 MB free) and
  read-only.
- **Load:** over 3 s with Move Remote idle, cores 0-2 were about 99 % idle. Core 3 was about 4-5 % busy (mr-audio:
  the SPI thread).
- **Listening ports:**
  - :80 is `/opt/move/MoveWebService` (uid ableton, no capabilities). **It keeps running while Move's software is
    stopped**, so :80 is taken in both modes.
  - :7700 schwung-manager, :7720 moveremote-host, :7681 display-server, :22 sshd, :53 dnsmasq.
- **Low ports:** net.ipv4.ip_unprivileged_port_start = 80, so the ableton user could bind :80 if it were free.
- **mDNS:** avahi-daemon runs (UDP 5353) and serves http and ssh services from /etc/avahi/services, which is on the
  read-only root fs.
- **HTTPS client:** wget and openssl are present (to be checked against GitHub in phase 2); there is no curl.
- **Schwung modules installed:**
  - audio_fx: chowtape, clap, cloudseed, dissolver, dragonfly-hall, freeverb, gate, granular, junologue-chorus, mverb,
    nam, psxverb, superboom, tapedelay, tapescam, usefulity;
  - midi_fx: arp, branchage, chord, eucalypso, euclidrum, genera, impressive-chords, superarp, velocity_scale.

## .rfm1 in wasm3 (FM1VST rfm1_run, cross-built, pinned to core 2)
- **The finding:** wasm3 on the A72 is about 14x slower than on the M-series Mac, not 5-6x. **It cannot carry the
  heavier firmwares.**
- Method: init, 4 s idle, then a chord held 5 s. "x real time" is how fast the firmware ran: the same as on
  remotefm1.com's RemoteFM1 builds.

| firmware | overall | chord held | load | boot |
|---|---|---|---|---|
| felucca 1.8.2 | 2.3x | 2.0x | 99 ms | 5 ms |
| choralroot 0.41 | 1.0x | 1.2x | 150 ms | 3 ms |
| ghoulbox 2.4 | 1.5x | 1.3x | 90 ms | 5 ms |
| loom 0.16.2 | 2.6x | 2.6x (silent: needs its test lines) | 92 ms | 3 ms |
| melodee 1.6.1 | 1.2x | **0.9x** | 187 ms | 56 ms |
| duell 1.3.1 | 1.2x | **0.9x** | 121 ms | 24 ms |

- Below 1x a firmware can't keep up at all. ChoralRoot and GHOULBOX would use 80-100 % of a core.
- Native, derived (not measured): on the Mac, native is 16x faster than wasm3 for Felucca and 24x for ChoralRoot.
  - So natively on the A72: about 30x real time, ~3-4 % of a core each. Three heavy firmwares come to ~10 % of a core.
  - wasm2c (the .rfm1 translated to C and compiled) usually reaches 50-80 % of native, ~5-7 % of a core each.

## What it changes
1. **wasm3 is out as the main runner on the Move.** Firmwares must run as native code there.
   - (a) wasm2c: the catalog's .rfm1 files translated and compiled for linux-aarch64. Same file, same sound; built by
     the catalog (RFM1Manager) or once on the Mac.
   - (b) FM1VST's cores built natively for linux-aarch64.
   - (a) keeps "everything is an .rfm1" (the owner's model) and covers author-built files. **Recommended**, with a
     spike first: one .rfm1 through wasm2c, timed on the Move.
   - wasm3 stays only as a fallback for light firmwares (Felucca class, ~45 % of a core) with fw_voices = 1.
2. **Address:** :80 is MoveWebService's in both modes. So it's `remotefm1.local:<port>` (our own mDNS name; avahi's
   service files are on the read-only root fs), or `move.local:<port>`. A link card in Schwung Manager's Tool tab
   helps.
3. **Storage:** /data/UserData/RemoteFM1 has plenty of room.
4. **Audio by ear:** not done yet. Move Remote is running and may have a host connected; a test tone would take it
   over. Waiting for the owner.

## The wasm2c spike (same day, the owner's OK)
- The same .rfm1 files went through wasm2c 1.0.32 (Debian bookworm's wabt, in a Docker image built on
  moveremote-move-build) and were compiled -O2 -ffp-contract=off for aarch64 with wasm-rt-impl.c.
- They ran in a ~200-line host (scratchpad probe/src/w2c_run.c) with exactly rfm1_run's clock and chord.

| firmware | wasm3 (chord) | wasm2c (chord) | wasm2c overall | worst audio() | load / boot |
|---|---|---|---|---|---|
| felucca 1.8.2 | 2.0x | **42x** | 46x | 16 us | 0.6 / 2.4 ms |
| choralroot 0.41 | 1.2x | **26x** | 22x | 279 us | 0.7 / 2.5 ms |

- **The audio is bit-identical to wasm3.** The md5 of the whole run's PCM matches for both firmwares, and so do the
  RMS, the peak and the LCD writes.
- Cost: about 2.5 % of a core (Felucca) and 4-4.5 % (ChoralRoot).
- **Three ChoralRoots at once,** one per core 0-2: 23-24x real time each, no slowdown.
- Felucca + 2x ChoralRoot all on core 2 (time-sliced by the OS): still 10-18x real time each.
  - So **three firmwares fit on one core**: ~12 % of a core for three heavy ones.
  - fw_voices = 3 looks possible in overtake mode too.
  - (The 16-20 ms worst blocks there are the scheduler slicing three processes. A host renders the three in turn on
    one thread.)
- Binary size: 1.4-1.9 MB per firmware (the C from wasm2c is 12-16 MB of source; compiling takes ~30 s each in
  Docker).
- Probe files on the Move: /data/UserData/rfm14move-probe (17 MB, includes the PCM captures). To be deleted.

**Conclusion:** the Move runs .rfm1 firmwares as wasm2c-compiled native code.
- Same file, same sound, ~20x faster than wasm3.
- Each catalog .rfm1 gets a linux-aarch64 build: a `.rfm1m` (name to settle) produced from the published .rfm1 in
  CI, with its SHA-256 tied to the .rfm1 it came from.
- Options for who builds it:
  - RFM1Manager publishes one beside each .rfm1;
  - or the Move build of RemoteFM14Move translates the bundled set.
  - The Move can't run wasm2c plus gcc itself (no compiler on the device).
- Author-built .rfm1 files work the same: the catalog CI translates them; the source is untouched.
